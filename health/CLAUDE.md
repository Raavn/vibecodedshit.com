# health

The Codebase Health benchmark CLI. Methodology v1.0 is in `methodology/v1.0/`; the YAML files are the source of truth for definitions, anchors and weights.

Run commands from this directory (`npm --prefix health <cmd>` from the repository root). Never add a `package.json` at the repository root: Vercel deploys the static site from there.

## Commands

- `npm run typecheck` runs `tsc --noEmit`
- `npm run lint` runs `eslint .`
- `npm run test` runs `vitest run`
- `npm run test:tools` runs the real Python tools (`pipx install complexipy vulture deptry import-linter && brew install osv-scanner gitleaks` first). Not part of `verify`. `HEALTH_UPDATE_FIXTURES=1 npm run test:tools` rewrites the `helper-out.json` files of the D3 Python fixtures from the real helper.
- `npm run test:docker` runs the Docker integration tests in `test/docker/` against the real image (`HEALTH_DOCKER=1`). Skipped otherwise, not part of `verify`. Build the image first with `npm run image:build`.
- `npm run image:build` builds `health:1.0` from `docker/Dockerfile`.
- `npm run verify` runs all three. Run it before every commit.
- `npm run build` emits `dist/`. `dist/` is committed (plugin installs don't build); `test/plugin/dist.test.ts` fails when it is stale, so run the build and commit it with any change under `src/`.
- The Claude Code plugin: `.claude-plugin/plugin.json` here, marketplace at `../.claude-plugin/marketplace.json`, skill in `skills/codebase-health/SKILL.md`. Keep `plugin.json` `version` equal to `package.json`.
- `npm run health -- scan <path> --preview` runs a preview scan and writes `./run.json`. Without `--preview` it is a full run: the execution steps run in the `health:1.0` image (Docker needed).
- `npm run health -- report <run.json> [--out <file>]` writes one self-contained HTML file (default `./health-report.html`, git-ignored) and prints its absolute path
- `npm run health -- diff <before.json> <after.json> [--json]` compares two runs (after minus before); `--json` prints one object, schema in `src/diff/compare.ts`

## Layout

- `src/methodology/`: loader and zod schemas. Anchors, weights, bands and the cap margin always come from the YAML, never from code.
- `src/scope/`: `git ls-files`, fixed exclusions, `.healthignore`, file roles, line counts, workspace packages. Python is parsed by `python/scope_helper.py` (stdlib only).
- `src/measure/`: one `Measurer` per parameter (`p4-2.ts`), listed in `registry.ts`. A measurer returns raw values per (package, language group) and never pools or scores.
- `src/tools/`: the injected `ToolKit` (resolve, run, fetch, memo), the tool catalog, work copies and the shared knip run. Measurers call tools only through `ctx.tools`; tests pass `fakeToolKit` from `test/helpers/tools.ts`. A missing or failing tool is `not_measured` in preview and a `ToolError` in full mode, never a score of 0.
- `src/measure/d3/`: D3 (architecture & boundaries). `p3-1.ts` to `p3-5.ts` turn per-language facts into raw values and never see a tool; `d3/ts/` is the TS/JS adapter (dependency-cruiser in process, `.dependency-cruiser` rules read without executing them, presets converted to rules); `d3/py/` is the Python adapter (`python/imports_helper.py`, stdlib, for statements and flags; `python/graph_helper.py` for grimp and import-linter, run with the interpreter named in the `lint-imports` shebang on a work copy). `getD3Rules` (no tool) and `getD3Graph` (needs the tool) are memoized per scan.
- `src/measure/deps/`: D5 (dependency & security hygiene). `declared.ts` (declared dependencies per unit), `lockfiles.ts` (the one place that knows lockfile formats), `resolved.ts` (declared to resolved version, lockfile level), `osv.ts` and `cvss.ts` (5.1 severity), `registry.ts` (npm and PyPI, as-of filtering). `severityPoints` and `majorsBehind` are pure so `health diff` can rescore 5.1 and 5.2. `src/util/pep440.ts` holds Python version logic.
- `src/scripts/`, `src/manifest/`, `src/scope/tracked.ts`: shared readers for CI files, entry points and tracked files. `scripts/entry-points/` has one kind per file (package.json, Makefile, justfile, tox, nox, pyproject tables); `expand.ts` follows calls up to 3 levels (3.1, 6.2, 6.4, 6.6); `checks.ts` turns a resolved command into typecheck, lint or test using the lists parsed from dimension 6 (`methodology.d6`); `triggers.ts` decides whether a CI job runs on pull requests or non-default pushes (6.4).
- `src/measure/safety/` (1.4, 1.5): TS import facts, module resolution against tracked files only, barrel following, test-case and assertion counting, and the Python import resolution. `python/tests_helper.py` gives the Python facts.
- `src/measure/ops/` (6.2, 6.5, 6.6): entry-point checks per directory, runtime pins, env reads (`python/env_helper.py` for Python), env example parsing, and the documented-command extraction and resolution. `python/nox_helper.py` reads `noxfile.py` sessions.
- `src/exec/` (6.1, 2.1, 2.5, 1.1-1.3, 6.3): the execution layer. The host orchestrates and the static layer stays on the host; only install, build, typecheck, lint, knip and the tests run in the image, one `docker run` each as the host uid:gid with `HOME=/tmp`, so the work copy stays removable on Linux (`docker.ts`, via an injected `spawn`; tests pass `fakeRunner` from `test/helpers/exec.ts`). Network-on steps (install, coverage-install) mount the host package cache at `/cache` and point npm, pnpm, Yarn, bun, pip, uv, poetry, pdm and pipenv at it, so repeated scans do not download the same packages again; `HEALTH_PACKAGE_CACHE` sets the directory (default `~/.cache/health/packages`) or `off`. `plan.ts` picks install roots and typecheck units, `steps/<name>.ts` has one step per file, `run.ts` runs them on a temp copy of the tracked files and reads the reports into `ExecutionResults` (`ctx.exec`). `p6-1.ts`, `p2-1.ts`, `p2-5.ts`, `p1-1.ts` to `p1-3.ts` and `p6-3.ts` are pure functions of `ctx.exec` and never start Docker. The test step (`steps/test.ts`) runs after lint, one invocation per directory chosen by `test-runners/detect.ts` (vitest, jest, mocha, node:test, pytest; unittest, tox and nox projects run through pytest). `test-runners/<runner>.ts` builds the argv and names the report files, `test-reports/` has one pure parser per report format (results and coverage are read from `/out`, never stdout), `tests.ts` holds the 1.1 to 1.3 measuring. Vitest installs its matching `@vitest/coverage-v8` in a network-on `coverage-install` step; a failure there, or a results report with cases but no coverage, is a `ToolError`. A timeout or no results report is a repository failure. 6.3 sums the typecheck, lint and test step durations; full runs also write them to run.json `execution.feedbackLoop`. Knip (`steps/knip.ts`, for 4.4 and 5.5) runs after lint, one step per knip root, with the empty config baked in at `/opt/health/knip.json`; `src/tools/knip.ts` reads those reports on a full run whose installs all worked, and runs the host's knip in the repository otherwise (preview, or a failed install). A knip step that crashes, times out or writes no usable report is a `ToolError`. `reports.ts` parses tsc, pyright, mypy, eslint and ruff output. A docker, image or exit 125-127 failure is a `ToolError` (invalid run); a timeout or a checker with no usable report is a repository failure (score 0).
- `docker/`: `Dockerfile` for `health:1.0` (every tool pinned), `config/` with the methodology's pinned `eslint.config.mjs`, `eslint.untyped.config.mjs` (same rules built by `eslint.rules.mjs`, no type information, for TS files outside every tsconfig) and `ruff.toml` (baked into the image, a repository's own lint config is never used), `bin/` with the small wrappers the steps call (`health-capture`, `health-eslint` (typed eslint, then an untyped relint of files the project service cannot place; Node heap raised to 75% of the container memory limit), `health-venv`, `health-tsc`, `health-pytest`, `health-coverage-install`).
- `src/scoring/`: pure scoring, pooling and aggregation.
- `src/run/`: `scan.ts` builds run.json, `recompute.ts` re-derives scores from stored raw values, `read.ts` reads and validates a run.json (zod) for `report` and `diff`.
- `src/commands/`: `report.ts` and `diff.ts` (`scan` is still in `cli.ts`). `report` and `diff` read run.json only and never recompute: the report renders in `src/report/` (template literals, `escapeHtml` for every dynamic string, no script, no external request, no clock); the diff is `src/diff/` (`conditions.ts` the five refusal conditions, `compare.ts` deltas and the regression flag, `format.ts` human output).
- `src/report-only/hotspots.ts`: churn (12 months, `git log`) times the per-file cognitive complexity 4.1 stores in `reportOnly.complexityByFile`. `scan.ts` stores the top 20 as `reportOnly.hotspots`; report-only values never enter scoring, `recompute` or the diff.

Adding a parameter: add `src/measure/p<d>-<n>.ts` and a test beside it, add one import and one entry to `registry.ts`, extend a fixture's `expected.json`. Do not change scoring, pooling, aggregation or the run.json shape (full runs add `tools.image`, the image tag and digest, and `execution.feedbackLoop`).

## Fixtures

`test/fixtures/<name>/` hold hand-counted repositories with `expected.json`. They are not git repositories; `test/helpers/fixture.ts` copies one to a temp directory and runs `git init` and `git add`. Fixtures are excluded from tsc, eslint and vitest on purpose. The `exec-tests-*` fixtures hold a hand-counted suite per runner with `expected.json`; the stored reports a fake runner writes are in `test/fixtures/reports/<runner>/`. The other `exec-*` fixtures are tiny repositories for the execution layer: each has a planted install failure, build failure, type error or lint finding and an `expected.json` that both the fake-runner tests (`test/exec.test.ts`) and the Docker tests read.

## Exit codes

0 ok, 1 usage error or unreadable input, 2 methodology error (no run.json), 3 no logic file (no run.json), 4 tool error (run.json with `valid: false`), 5 `diff` refused (the runs are not comparable). A regression flag never changes the exit code.
